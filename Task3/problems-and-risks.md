# Task3: проблемы, риски и решение Event-Driven

## Текущие проблемы

- `core-app` и `ins-comp-settlement` получают каталог продуктов через REST polling к `ins-product-aggregator`. Потребители зависят от доступности агрегатора и от задержек внешних API страховых компаний.
- `ins-product-aggregator` при синхронном запросе обращается ко всем страховым компаниям, агрегирует ответы и только после этого возвращает результат. При росте числа интеграций с 5 до 10 увеличиваются задержки, timeout-ы и вероятность частичных ошибок.
- Локальные реплики продуктов и тарифов в `core-app` и `ins-comp-settlement` обновляются по расписанию. Между обновлениями данные могут устаревать, а при ошибке очередного polling-цикла отставание реплики сохраняется до следующего успешного запуска.
- `ins-comp-settlement` раз в сутки запрашивает в `core-app` все оформленные за день страховки. Такой batch-запрос создаёт пиковую нагрузку ночью и связывает расчёты с доступностью `core-app`.
- Синхронные REST-связи создают каскадную деградацию: сбои во внешних страховых API влияют на `ins-product-aggregator`, затем на `core-app` и `ins-comp-settlement`.

## Риски роста нагрузки

- Подключение ещё пяти страховых компаний почти удваивает число внешних запросов, которые должен выполнить `ins-product-aggregator` для актуализации каталога.
- Рост пользовательского трафика увеличивает требования к свежести и доступности продуктовой реплики в `core-app`.
- Рост количества оформленных страховок увеличивает объём данных, которые `ins-comp-settlement` должен получить и обработать при ночном batch-сценарии.
- Повторные polling-запросы плохо масштабируются: при росте нагрузки потребителей возрастает нагрузка на источник, хотя данные нужны им для локального чтения.

## Целевое решение

- Добавить `Kafka / Event Broker` и использовать event streaming для репликации данных между сервисами.
- `ins-product-aggregator` публикует изменения продуктов и тарифов в `product-catalog-events`.
- `core-app` и `ins-comp-settlement` подписываются на `product-catalog-events` и обновляют локальные реплики без REST polling к `ins-product-aggregator`.
- `core-app` публикует событие `insurance_policy_issued` в `policy-events` после оформления страховки.
- `insurance_policy_issued` содержит данные, необходимые для взаиморасчётов: идентификаторы полиса, клиента, продукта, тарифа и страховой компании, премию, статус и время оформления.
- `ins-comp-settlement` подписывается на `policy-events`, поддерживает локальную реплику оформленных страховок и формирует реестр взаиморасчётов без ежедневного REST-запроса в `core-app`.
- Outbound-интеграции `ins-product-aggregator` со страховыми компаниями остаются REST/SOAP/GraphQL: внешние страховые API остаются источником продуктов и тарифов.

## События

- `product-catalog-events`: `insurance_product_upserted`, `insurance_product_disabled`. Ключ партиционирования: `companyId + productId + tariffId`.
- `policy-events`: `insurance_policy_issued` с данными для взаиморасчётов. Ключ партиционирования: `policyId`.
- Каждое событие содержит `eventId`, `eventType`, `occurredAt`, версию схемы и идентификаторы доменной сущности.
- Потребители сохраняют обработанные `eventId` в технической таблице и игнорируют дубли.

## Transactional Outbox

- `core-app` использует Transactional Outbox: запись оформленной страховки в `core-db` и запись события `insurance_policy_issued` в outbox выполняются в одной транзакции.
- `ins-product-aggregator` использует Transactional Outbox при сохранении снапшота или дельты каталога, чтобы состояние каталога и публикация `product-catalog-events` не расходились.
- Outbox publisher отправляет события в Kafka асинхронно. Повторная публикация возможна, поэтому consumers должны быть идемпотентными.

## Риски Event-Driven и меры контроля

- Eventual consistency: локальные реплики могут отставать. Контроль: monitoring consumer lag и возраста последнего обработанного события.
- Дубли событий: модель доставки фактически at-least-once. Контроль: идемпотентность по `eventId`.
- Нарушение порядка: параллельная обработка может перепутать события одной сущности. Контроль: стабильный partition key.
- Потеря события без outbox: сбой между записью в БД и публикацией в брокер приводит к расхождению реплик. Контроль: Transactional Outbox у producer-сервисов.
- Ошибки обработки consumers: некорректное событие или временная ошибка может остановить поток. Контроль: retry/DLQ, алерты и replay из Kafka-топиков.
